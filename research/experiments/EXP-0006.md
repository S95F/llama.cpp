# EXP-0006 - Pin by a run's own first selections (online profile), with the launch headroom held fixed

**Status: complete. Decision: Adopt** the opt-in `LLAMA_MOE_PIN_ONLINE=<N>`
(pin the experts the run's own first N decode passes select most; no trace file
needed). It is for when no profile from the same kind of text exists; against a
matching file profile it gains nothing warm and costs time up front. The
defaults are unchanged. Also adopt the fixed launch headroom, the warm-up run
and the balanced order as the harness for timing experiments. Iteration 6,
authorized 2026-10-31. This is ROADMAP **R17**, timed with **R16**'s fixed RAM
headroom, plus the out-of-domain question **Q17**.

In one paragraph: all four hypotheses hold by their falsifiers, two of them
narrowly. Warm (tokens 387-1022), the online profile is within 1 ms per token of
the file profile at both caps (on64 +0.65, on128 -0.16, on64x15k +0.83,
on128x15k +0.90 ms), but slower in both rounds in three of the four arms, and
part of that is a first-touch transient after the registration that fades by
about token 640. Over the whole generation it beats address order at the default
cap by only about 1% (-0.47 and -0.54 ms per token; predicted -2 and -1), and it
trails the file profile by about 3.5 ms per token (3 s per 1024-token run),
because every pass before the registration is pageable (75-92 ms per token) and
the registration takes 0.54-0.57 s (the registering pass 0.62-0.66 s). On a
children's story (a different topic and register from the profile's text), the
file profile leaves 12.2 points more of the warm upload bytes pageable than on
prompt a, and the online profile is 2.25 ms (6.2%) faster than it warm; end to
end the online run is 0.64 s ahead. Reps agree within 0.8% and no run-position
drift is detectable (slope +0.011 ms per position). The offline replay
reproduces the measured pageable share of every arm within 0.2 points (0.1 after
fixing a one-pass offset in its windows), but converting share to milliseconds
overestimated the gains by up to 1.5 ms, because the pageable remainder
expert-level pinning leaves faults more per byte than address order's and the
online arms' early passes were slower than assumed. At 15000 MiB the online
registration stalls one token for 1.4-1.8 s.

## Hypotheses

**H1 (R17, warm)** - at the same cap, pinning by the selections of the run's
first N decode passes (N = 64 or 128) is within 1 ms per token of the file
profile on tokens 387-1022.

**Falsified by** an online arm more than 1 ms per token slower than the file
profile at the same cap (mean of reps), with the sign agreeing in both rounds.

**H2 (R17, cost)** - at the default cap, the online arms beat address order
over the whole generation (tokens 3-1022), the passes before the registration
and the registration itself included; and the registration takes under 1 s.
Expected margins: about -2 ms per token for on64 and -1 to -2 ms for on128
(a rebuild from EXP-0005's per-token timelines: `off` up to pass N, `prof7842`
after, plus the registration).

**Decided on** the mean of the two reps (ABBA) over tokens 3-1022, with the same
sign in both rounds. **Falsified by** an online arm whose mean is not below
address order, or whose sign differs between rounds, or a registration of 1 s
or more. If H4 is falsified (run-position drift persists), H2 is undecided,
not falsified.

**H3 (Q17, transfer)** - the file profile transfers worse to a prompt unlike its
own than to prompt a. At the default cap, `ood-prof` leaves at least 5 points
more of the warm upload bytes pageable (tokens 387-1022, CUPTI
`1 - pinned_share`) than `prof` in this session (EXP-0005: 22.3%). The online
profile's warm lead over the file profile is also larger on the out-of-domain
prompt: (`ood-prof` - `ood-on128`) > (`prof` - `on128`) on tokens 387-1022 in
both rounds.

**Falsified by** `ood-prof`'s pageable share within 5 points of `prof`'s, or
(`ood-prof` - `ood-on128`) <= (`prof` - `on128`) in either round. Also
reported, in relative terms only because the text and the miss bytes differ
between prompts: (`ood-addr` - `ood-prof`) / `ood-addr` against
(`addr` - `prof`) / `addr`.

A note on the register: the profile (prompts b, c and d) and prompt a are mostly
text inside the model's `<think>` block, planning bullets. Prompt a's
1024-token run never leaves it (EXP-0005's stdout has no `</think>`), and of the
profile's prompts only c answers without thinking. So `prompt_ood.txt` changes
both the topic and the register: it asks for a children's story and ends with
an empty think block (`<think>\n\n</think>\n\n`), so the story is generated as
the answer. The completion tool tokenizes the raw prompt with special tokens.

**H4 (R16)** - with the available RAM at launch held at one value for every run,
reps of one arm agree within 2% warm, and the r1 - r2 difference no longer
grows with the gap between the reps.

**Falsified by** any arm's warm reps more than 2% apart; or a least-squares
slope of (r1 - r2) against the rep gap across the 10 arms (tokens 387-1022)
above half of EXP-0005's, 0.05 ms per position; or r1 slower than r2 in at
least 8 of the 10 arms. EXP-0006 holds one headroom level, so it tests only the
reproducibility half of R16; the prefill clause (slow copies rising with the
balloon) stays open.

## Offline predictions (before any timed run)

`traces.sh` took one untimed 1024-token trace per prompt (no pinning, no
Nsight; routing and the cache do not depend on either), and `coverage.py`
replayed them through EXP-0005's simulator at 2048 MiB and scored every order
on the windows the runs measure (`coverage_1024.json`). The simulator matches
the recorded fills exactly (123521 for prompt a, 86205 for the story). Prompt
a's trace run printed the same 1024 tokens as EXP-0005's timed runs, and its
address and file-profile shares (50.7%, 22.4%) match what CUPTI measured there
(50.7%, 22.3%). The story prompt was answered as a story, outside any think
block, and misses 29% fewer bytes per token (157 against 221 MiB).

Pageable share of the upload bytes:

| a, default | 3-1022 | 51.7% | 22.4% | 28.2% | 29.2% |
| a, 15000 MiB | 387-1022 | 20.2% | 2.3% | 6.8% | 4.2% |
| a, 15000 MiB | 3-1022 | 20.5% | 2.3% | 12.7% | 16.1% |
| story, default | 387-1022 | 49.1% | 34.6% | 15.7% | 11.6% |
| story, default | 3-1022 | 49.2% | 34.0% | 20.8% | 22.1% |

These replace the plan's first figures (online 18.8% and 13.6% at the default
cap), which were scored on tokens 128-255 of 256-token traces. On the warm
window the online profile is no better than the file profile on prompt a: N =
64 leaves 2.5 points more pageable, N = 128 2.1 points less. On the story it
leaves 19 to 23 points less.

Converted with EXP-0005's slopes (0.125 ms per point at the default cap, 0.163
at 15000 MiB; for the story scaled by its 0.71 miss bytes), warm, against the
file profile at the same cap: on64 +0.3 ms, on128 -0.3 ms, on64x15k +0.7 ms,
on128x15k +0.3 ms. **H1 is predicted to hold**, with on64x15k the closest to
the 1 ms line. **H2**: about -2 ms (on64) and -1 ms (on128) against address
order over tokens 3-1022, from the 23 to 24 points of whole-run share less
the slow pageable passes before the registration. **H3**: the file profile's
share rises by 12.2 points on the story (falsifier: under 5), and the
difference of differences is about +1.8 ms (the story's online lead about 2.0
ms, prompt a's about 0.3 ms). The file profile's relative gain over address
order shrinks from 56% of the pageable share on prompt a to 30% on the story.
Level 4 until measured.

A risk the predictions do not price: after the eviction, the experts the first
N passes never selected are not in RAM. At 15000 MiB the registration also
pins unselected experts as filler, and locking them reads them from disk, so
the registering pass may take seconds there. From the traces, the first 64
passes of prompt a select 4326 experts (about 7925 MiB), the first 128 select
5240 (about 9600 MiB); on the story, 3411 and 4077 (6249 and 7469 MiB). So the
filler is about 7 GiB for on64x15k, 5.4 GiB for on128x15k, 0.5 GiB for
ood-on128 and close to nothing for on64 and on128 at the default cap. H2's
1 s registration limit applies at the default cap only.

## Design

**Code.** `LLAMA_MOE_PIN_ONLINE=<N>` (with `GGML_CUDA_REGISTER_HOST=1`): pin
nothing at load; count the experts selected by each small batch (up to 8
tokens) for N passes; at the start of pass N + 1, after the router read-back
and before the uploads (the stream is idle there), rank the experts by count
and register them under the pin cap, exactly as `LLAMA_MOE_PIN_PROFILE` ranks a
trace. Ranges are registered most selected first, so a driver refusal drops
the least selected; refused bytes are logged. Registration holds the
process-wide range table's lock. Logged with its duration.

**Arms** (2048 MiB cache, all with `GGML_CUDA_REGISTER_HOST=1`, 1024 tokens,
two reps, ABBA):

| arm | cap | order |
|---|---|---|
| `addr` | default | address |
| `prof` | default | file profile (EXP-0005's `profile_bcd.csv`) |
| `on64`, `on128` | default | online, N = 64 / 128 |
| `prof15k` | 15000 MiB | file profile |
| `on64x15k`, `on128x15k` | 15000 MiB | online |
| `ood-addr`, `ood-prof`, `ood-on128` | default | as above, on `prompt_ood.txt`, with `--ignore-eos` |

Address order at 15000 MiB is left out: at EXP-0005's headroom it went below
300 MiB available, and a fixed launch headroom of 19.5 GiB would leave it less.

**Order.** One discarded warm-up run (`on64x15k_w`) first; it also checks that
15000 MiB still registers (at least 14800 MiB) with the balloon's locked pages
present and that the run stays above the kill floor, or the session stops.
Then `prof on64 addr on128 prof15k on64x15k on128x15k` forward and reversed,
so `addr` sits next to each online arm in both rounds, then
`ood-addr ood-prof ood-on128` forward and reversed.

**Headroom (R16).** After `evict.py` and `probe.py`, `balloon.py` allocates and
locks private memory until 19968 MiB (19.5 GiB) is available, and holds it to
the end of the run. A balloon that ends more than 192 MiB off the target, or
unlocked, is released and retried after a new eviction, up to three times; a
run that still misses it goes ahead and is flagged (`flag_<tag>.txt`). The
session stops before a run if another `llama-completion.exe` is running.

Expected at a 19968 MiB launch (EXP-0005, shifted): `prof15k` minimum about
0.7 GiB available and warm median about 1.05 GiB; `on64x15k` about 0.3 GiB
lower; `on128x15k` about 0.05 GiB lower. If `monitor.py` kills a run, every
comparison with that arm uses the matched window up to its last complete
token, as EXP-0005 did; a run whose warm median available RAM is below 1 GiB is
flagged as headroom-limited.

**Windows.** Warm 387-1022; whole generation 3-1022; early 3-130; for online
arms also passes 3 to N, the registration pass N + 1, and N + 2 to 386.

**Also recorded**: per-process working set, private bytes and page faults
(`monitor.py`, every second), the standby, modified and free page lists and the
working set of all processes (typeperf; the other processes' share is the total
less the benchmark and the balloon), the registration time and the registering
token's time, and each run's stdout with its hash: every run of one prompt must
print the same 1024 tokens (B3 covers only 256).

### The online profile's cost is up front

Where the online arms' 3-1022 time against the file profile goes, seconds per
run (r1, r2):

|---|---:|---:|---:|---:|---:|
| on64 - prof | +3.57, +3.74 | +1.89, +1.94 | +0.56, +0.59 | +0.75, +0.76 | +0.37, +0.46 |
| on128 - prof | +3.11, +4.07 | +2.69, +3.04 | +0.56, +0.55 | +0.16, +0.38 | -0.29, +0.09 |
| on64x15k - prof15k | +7.47, +6.90 | +3.26, +3.11 | +1.72, +1.75 | +1.88, +1.60 | +0.62, +0.44 |
| on128x15k - prof15k | +7.70, +7.81 | +4.71, +4.74 | +1.39, +1.46 | +1.08, +1.00 | +0.52, +0.62 |

- **Before the registration every expert copy is pageable**: 91 ms per token
  over passes 3-64 for on64 and 75-77 ms over 3-128 for on128, against prof's
  53.5 ms over 3-130. The page cache is not cold then: the load's prefetch read
  most of the file before token 3, so these passes mostly first-touch standby
  pages (soft faults), plus about 1.0-1.4 GiB re-read from disk (system-wide
  counter).
- **After the registration the deficit fades by about token 640.** Split post
  hoc, online minus file profile on 387-642 and 643-1022: on64 +1.33 then
  +0.19 ms, on128 +0.57 then -0.65 (-0.93/-0.36, faster in both rounds),
  on64x15k +1.69 then +0.25, on128x15k +1.82 then +0.28. That is consistent
  with first-touch faults on experts the registration left pageable (not shown
  directly). So the warm window is not yet steady state for the online arms,
  and in its second half on128 is the faster.
- **On the story the early cost is paid back within the run.** ood-on128 loses
  2.3 s before and at the registration and wins it back after; decode alone
  ends 0.13 s behind ood-prof at token 1022, a break-even near token 1080 by
  extrapolation of the -2.25 ms per token warm lead. End to end it is already
  0.64 s ahead, because ood-prof pays its registration at load (below).

### Registration cost

| | register calls | after them | registering token |
|---|---|---|---|
| on64, on128 (default cap, 7104-7392 ranges) | 544-565 ms (0.075-0.078 ms per range) | no stall (next sync 1 ms) | 615-658 ms |
| ood-on128 (6501 ranges) | 587-593 ms | no stall | 629-633 ms |
| on64x15k (2832 ranges) | 1681-1766 ms, one call 1517-1571 ms | no stall | 1759-1845 ms |
| on128x15k (3420 ranges) | 188-198 ms | next stream sync 1183-1260 ms, GPU idle | 1422-1490 ms |
| addr at load (50 ranges, 7842 MiB) | 2-3 ms | GPU-idle sync 884-1061 ms before the prompt read-back | (before token 1) |
| prof at load (7299 ranges) | 597-616 ms | GPU-idle sync 957-1217 ms | (before token 1) |
| prof15k at load (4881 ranges, 14924 MiB) | 262-286 ms | GPU-idle sync 2757-2893 ms | (before token 1) |

H2's limit (1 s) holds at the default cap. At 15000 MiB the online
registration stalls one token for 1.4 to 1.8 s in every rep (warm-up
included). The stall sits in a different call in the two arms but is about the
same size. During it the process takes 1.3 to 1.6 million page faults over two
1 s samples, its working set grows 4.9 to 6.0 GiB (the predicted filler of
unselected experts is 5.4 to 7 GiB), available memory falls 5 to 6 GiB, and
the disk reads 1.5 to 2.1 GiB. The default-cap registrations show none of
this.

**The pre-run guess was half right.** Registering pages that are not in RAM can
return without reading them: addr registers 7.66 GiB of evicted pages at load in
2-3 ms (mid-run, on64x15k's stall is inside one register call). But a long
GPU-idle stream synchronization follows every load-time registration (0.9 to 2.9
s, longest at 15000 MiB), and the arms that pin nothing at load have at most 53
ms there. So paging in the registered pages costs about the same at load and
mid-run; at load it is hidden before the first token, mid-run it lands in one.
The smoke run (no balloon, no eviction, no Nsight) logged 14.57 GiB registered
in 164 ms; whether a stall followed was not measured. Paging in non-resident
pages is the leading candidate cause, with the balloon's pressure second. The
driver-level mechanism is unknown.

### Out of domain (H3)

The story was answered as a story, after the empty think block, and uploads
29% fewer bytes per token than prompt a (157 against 221 MiB). Warm:

- the file profile leaves 34.5% of the bytes pageable there, against 22.3% on
  prompt a, and gains only 1.5% over address order (7.9% on prompt a), the
  same sign in both rounds;
- the online profile leaves 11.6% and is 2.25 ms (6.2%) faster than the file
  profile (-2.30/-2.19), 2.79 ms faster than address order;
- over 3-1022 the three story arms tie (range 0.13 ms on the means; ood-prof
  is fastest in both rounds, by 0.08-0.18 ms, inside the rep spreads);
- end to end, ood-prof is the slowest of the three: 0.91 s behind ood-addr,
  0.64 s behind ood-on128.

**The file profile's small gain on the story is not explained by its share.**
It leaves 14.6 points less pageable than address order, yet has more
slow-copy (hard-fault) idle: 2.79 against 1.69 ms per token. Its slow copies
rise from 1.07 to 1.76 per token despite 30% fewer pageable copies, and system
page input is about 1.6 times higher. Had slow-copy idle scaled down with the
pageable bytes, the gain would have been about 2.1 ms instead of 0.54. Prompt a
shows the same pattern: prof and on128 make 2.1 to 2.3 slow copies per token
against addr's 1.6.

Every slow copy is pageable (joined to its API call; tokens 387-1022, r1). What
changes is the share of pageable copies that fault: 0.9% under address order
(1.6 of 183 per token), 2.0% for ood-prof, 2.7% for prof (2.2 of 80), 12% for
prof15k (1.0 of 8). Per pageable GiB that is 14 slow copies under address order,
33-101 under the profiles at the default cap and 80-203 at 15000 MiB. **Level 4
explanation**: a profile pins the hot experts, so its pageable remainder is the
cold tail, selected rarely, whose pages have left RAM between uses; address
order leaves whole layers pageable, hot experts included, and those stay
resident. Which experts fault was not identified (the copy records carry no
address).

### Upload fragments under expert-level pinning

Expert slices are not page-aligned, so pinning at page granularity splits the
uploads of neighbouring experts at the pinned edges into tiny pinned pieces:
67 to 84 pinned copies under 4 KiB per token under the file and online
profiles at the default cap (30 for ood-on128), against 7 under address order.
Copies under 8 KiB are then 21-33% of host-to-device copies (11-15% under
address order, where they are the fixed small non-expert copies). Pinned copies
average 415-552 KiB against 589-599, at 11.5-12.5 GB/s busy rate against 12.8.

**The fragments are not the reason the story gains little.** They cost about
0.2 ms per token of DMA and about 0.1 ms of GPU idle. The lower pinned rate
comes mainly from big pinned copies that follow a pageable copy or a fragment,
and it is offset by faster pageable copies (10.1-10.6 against 8.7 GB/s):
ood-prof's DMA time falls 0.95 ms per token against ood-addr's, matching the
0.89 ms expected from moving 24 MB per token to pinned memory. The shortfall is
the slow-copy idle above.

### Memory

- **At the default cap the online profile uses less RAM**, because it pins
  only experts the run uses. Warm working set: on64 and on128 16457-16539 MiB,
  prof 17013-17025, addr 18289-18295; on the story ood-on128 14938-14945
  against ood-prof 16679-16781. Warm median available is 0.4-1.0 GiB higher
  than prof's on prompt a and 1.8 GiB higher on the story.
- **At 15000 MiB it uses more.** Warm median available: online 465-774 MiB
  against prof15k 859-1060; lowest during decode 315-476 against 548-776;
  warm working set 19195-19520 MiB (18.7-19.1 GiB) against 18864-18878 (18.4
  GiB). The pageable remainder the online sets leave holds experts the run
  selects later, and they stay resident. 5 of the 6 runs at 15000 MiB had a
  warm median below 1 GiB available, so H1 at 15000 MiB is headroom-limited.
- **The warm-up went below the floor.** on64x15k_w reached 264 MiB, below the
  300 MiB floor for about 5 s (the monitor kills after 20 s). runs.sh's check
  looks only for a kill, so the session went on. A protocol gap, recorded here;
  the plan said the warm-up checks the run stays above the floor.

### Reproducibility (H4)

Every warm r1 - r2 is within 0.32 ms (EXP-0005: +0.41 to +1.71). The slope
of r1 - r2 against the rep gap is +0.011 ms per position (SE 0.020, 95% CI
-0.036 to +0.058; +0.033 on the seven prompt-a arms alone). EXP-0005's slope,
recomputed the same way, is 0.13, so the falsifier (0.05) was about 40% of it,
not half as the plan said. A drift of EXP-0005's size is excluded; one of half
that size is not. Several things changed at once (the balloon's fixed launch
headroom, lower than EXP-0005's: 19966-20022 against 20242-21703 MiB; a
warm-up run; another arm set and order, with no fully pageable arm and no
balloon-free control), so the result is not attributed to the headroom alone.

### Against EXP-0005

The three arms repeated from EXP-0005 ran slower here, warm: prof 41.73
against 40.42 ms, addr 45.32 against 43.97, prof15k 37.11 against 36.43. Both
reps are slower than both of EXP-0005's in each arm, with the same pinned MiB,
ranges, profile file (same hash), flags, prompt and pinned share. Most of the
extra time is slow-copy idle (prof +1.38 of +1.31 ms, addr +1.09 of +1.35,
prof15k +0.66 of +0.68), consistent with the lower launch headroom or the page
cache, which was not tested (one headroom level).

- **B3** (`check-correctness.sh`, 256 tokens, every expert on the GPU), after

## Conclusions

**Decision: Adopt** `LLAMA_MOE_PIN_ONLINE` as an opt-in. Defaults unchanged.

1. **Online pinning reaches the file profile's warm speed, not more**, at the
   same cap on the profile's own kind of text: within 1 ms, slower in both
   rounds in three of four arms, with a first-touch transient after the
   registration that fades by about token 640.
2. **Its cost is up front**: pageable passes before the registration and the
   registering pass, about 3 s per 1024-token run against a matching file
   profile at the default cap (6-7 s at 15000 MiB, with a 1.4-1.8 s stall).
   Against address order it still wins, by about 1% over the generation and
   0.5-1.0 s end to end.
3. **It wins where the profile does not match the text.** On one
   out-of-domain prompt the file profile kept only a 1.5% warm gain over address
   order and the online profile was 6.2% faster than it warm, 0.64 s ahead end
   to end. Q17 is answered for one prompt: a profile from one register
   transfers poorly to another.
4. **Holding the launch headroom fixed, with a warm-up run and a balanced
   order, left no detectable run-position drift** (R16's reproducibility half;
   the prefill clause is untested).
5. **The offline replay reproduces the pageable share of any order to 0.1
   points on a known token sequence, but share does not convert to time at one
   rate**: the remainder expert-level pinning leaves pageable faults more per
   byte.

### Limitations

- One host, model, cache size (2048 MiB), batch 1, greedy, one in-domain and one
  out-of-domain prompt, 1024 tokens, two reps per arm.
- Every number is traced (Nsight). End to end includes model load, which varies
  by up to about 0.45 s.
- The 15000 MiB comparisons are headroom-limited (warm median below 1 GiB
  available in 5 of 6 runs).
- The warm window is not steady state for the online arms; the 387-642 and
  643-1022 split was done after the fact.
- One headroom level: the prefill half of R16 and the cause of the slower
  session (against EXP-0005) are untested.
- The story-arm break-even near token 1080 is an extrapolation past the
  measured 1024 tokens.

### Next steps

Ranked; ROADMAP.md has the reasoning.

1. **Why the pageable remainder of expert-level pinning faults more per byte**
   (new Q18): 2.7% of prof's pageable copies are hard faults and 12% of
   prof15k's, against 0.9% under address order. Attribute faults to experts
   (log the host address of slow copies), and test keeping the cold tail
   resident (touching or prefetching it) against the RAM it costs.
2. **A hybrid profile**: the file profile at load, re-ranked from the run's own
   selections after N passes. It needs unregistering, and registering in
   chunks across passes would spread the stall.
3. **The registration stall** at 15000 MiB and the GPU-idle sync after every
   load-time registration: residency of the registered pages (non-resident
   filler, the file still being prefetched at load, WDDM residency at the first
   submission).
4. **Longer and more varied runs**: 2048 tokens or more to measure the online
   break-even directly, more out-of-domain prompts that separate topic from
   register, and end-to-end untraced timing.
5. **Close R16's prefill half**: two or more headroom levels.
6. Fix runs.sh's warm-up check to stop below the 300 MiB floor, not only on a
   kill.
