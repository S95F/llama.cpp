# EXP-0005 - Pin up to the budget, most-selected experts first, from a fixed page-cache state

**Status: complete. Decision: Adopt** the opt-in `LLAMA_MOE_PIN_PROFILE`
(pin the experts a selection trace uses most, instead of whole tensors in
address order). Also adopt the upload split at pinned-range edges, which
expert-level pinning requires. The defaults are unchanged. Iteration 5,
authorized 2026-10-31. This is ROADMAP **R11**, with **R10**'s controlled
baseline and **R5** (`--load-mode none`) as a comparison arm.

In one paragraph: at a 2048 MiB cache, the warm token (tokens 387 to 1022) falls
from **52.95 ms pageable to 36.43 ms (-31%)** when 14924 MiB of the experts the
selection profile uses most are pinned. Pinning the same amount in address order
gives **39.35 ms on the matched tokens 387-841, where profile order gives 36.65:
profile order is 2.69 ms (6.8%) faster** in both rounds. At the default cap
(RAM/4), profile order is **3.55 ms (8.1%) faster** than address order (40.42
against 43.97 ms). Profile order leaves 2% of the warm upload bytes pageable,
against 20% for address order. An offline model replays those shares to within
0.1 points over the tokens its traces cover, and within 3.1 points over the warm
window. The code splits host uploads at both edges of a pinned range, but only
one split is required: the win needs every upload split where it runs out of a
pinned range, because the driver rejects a copy that starts in registered memory
and runs past it. R10 did not hold: evicting the model before every run made the
page cache reproducibly cold at launch, but reps still drifted with run
position and, inseparably in this design, with the session's free RAM.
Separately, **the B3 correctness gate turned out to compare CPU and GPU
arithmetic**. At 256 tokens the cache-off reference diverges from every cache
configuration, because cache-off computes the experts on the CPU. With all
experts computed on the GPU, all ten configurations, including both pinning
orders, are byte-identical.

## Hypotheses

**H1 (R10)** - with the page-cache state fixed at the start of every run (the
model evicted, residency verified), reps of one arm agree within 3% warm, and
the prefill coldness check reproduces.

**Falsified by** reps differing by more than 3% under the fixed state.

**H2 (R11, the cap)** - pinning about 15000 MiB cuts the warm 2048 MiB token to
42 ms or less (EXP-0004 projected 38 to 39 for address order).

**Falsified by** a warm token above 46.6 ms (the 42%-pinned figure of EXP-0004)
at about 15000 MiB.

**H3 (R11, the order)** - at the same pinned MiB, pinning the most-selected
experts beats address order.

**Falsified by** profile order not beating address order in time per token,
with the sign agreeing in both rounds.

**H4 (R5)** - capped in-place pinning beats `--load-mode none`, which ROADMAP
expected to pin all 18.3 GiB or fail to allocate.

**Falsified by** `--load-mode none` matching or beating it.

**Outcome.**
- **H1 falsified, in part.** The probe found 0-7 of 256 expert pages cached
  before every run. Warm spreads were 1.1-3.9%, two of six arms above 3%. In
  tokens 3-130 the spreads were 11-28% in four of six arms. The prefill
  coldness check did not reproduce.
- **H2 holds**: 39.35 ms for address order (matched window) and 36.43 for
  profile order.
- **H3 holds** at both caps, in both rounds.
- **H4 is mixed.** `--load-mode none` is about 80% pinned, not 100%, and runs at
  38.21 ms (matched window). That is 1.14 ms faster than address order at
  15000 MiB but 1.56 ms slower than profile order. It also takes 15 s to load
  instead of 6.3-7.5 s.

## Motivation

EXP-0004's Finding 10 bounded the levers that are left. Pinning up to the
Windows pinned-memory budget was the largest one this host allows: a projected
-17 to -18 ms per token warm. It needs no new code for the cap
(`LLAMA_MOE_PIN_MIB`). But address order leaves the top layers pageable whatever
their traffic, so the order of what gets pinned was the open design question.
EXP-0004 also found that run order leaked page-cache state between runs, so
every comparison needed a fixed starting state first (R10).

## Code changes

`src/llama-moe-cache.cpp`, `src/llama-moe-cache.h`, `src/llama-context.cpp`:

| change | what it does |
|---|---|
| `LLAMA_MOE_PIN_PROFILE=<trace>` | Reads a selection trace in the `LLAMA_MOE_CACHE_TRACE` format and counts selections per (layer, expert), small batches only. Under the pin cap it then pins, in order of selection count, the page-rounded slices of every expert tensor of that expert. Ties and unseen experts go in address order, first fit, merged. Opt-in: without it, pinning is unchanged |
| upload split | `llama_moe_cache_set_async` splits every host-to-device upload of expert data at the bounds of the pinned ranges: where a copy leaves one (required) and where it enters one (so that its pinned part goes by DMA). The cache fills, the large-batch uploads, and, while anything is pinned, the scheduler's whole-tensor fallback all go through it |
| process-wide range table | The ranges pinned by every MoE cache of the process, under a mutex. A second context on the same model registers nothing, because the pages are already registered, but still splits at the first context's ranges |
| unusable profile | Unreadable, or no selections: a warning, then whole tensors in address order |
| log line | `registered X MiB ... (Y MiB left pageable) in N ranges`, where pageable is the total minus what was pinned |

`moe-bench/check-correctness.sh` gains a `cache2048-pinprof` arm (set
`PIN_PROFILE`, default cap), runs 256 tokens instead of 64, computes every
configuration's experts on the GPU (`GGML_OP_OFFLOAD_MIN_BATCH=1`, see

## Method

**Offline first (R11's "check before writing code").** `coverage.py` replayed
the four EXP-0001 traces through the simulator. Its fill counts reproduced the
recorded ones exactly (31516, 31762, 28360, 32893). It then scored the pinning
orders. At 15000 MiB, held out (the profile built from the other three
traces):

| order | pageable share of miss bytes, prompt a | prompts b, c, d |
|---|---:|---:|
| address (the code) | 21.3% | 20.7-21.2% |
| layer (whole tensors, most missed first) | 15.7% | 14.0-16.7% |
| expert (most misses per byte first) | 2.1% | 4.6-5.6% |
| select (most selections first) | 2.1% | 4.6-5.7% |

At the default cap address order leaves 53.8% and select 20.7% (b, c, d:
26.8-29.3%). Only expert-level orders do much better than address order. So the
code went in, using selection counts: they need no simulator and are what the
trace records.

**Fixed starting state (R10).** Flushing the standby list needs admin rights, so
before every run `evict.py` committed and touched 19456-20992 MiB until
available RAM fell to 0.50-0.75 GiB (512-766 MiB), then freed it. `probe.py`
then sampled 256 random expert pages with a seed derived from the run tag: 0-7
of 256 were cached before every run. A separate calibration after the runs read
the whole GGUF with `cat`. The disk counter summed 20.63 GiB, and the probe
found 254 of 256 pages cached, so the counter and the probe are sound
(`calib_disk_counter.txt`).

**Per run**: typeperf paging and disk counters every second, the watchdog, then
one 1024-token traced generation (B7). Prefill coldness check: the expert copies
before the first logits read-back, and how many ran below 1.5 GB/s on the host
side (EXP-0004's classifier).

**Windows.** Tokens 387-1022 (warm, EXP-0004's), 3-130 (early), and **387-841,
matched** to addr15000_r1, which the watchdog stopped after 842 decode steps
(839 analyzed tokens; available RAM below 300 MiB for 20 s, lowest 205 MiB).
Tokens 842-1022 run faster than 387-841 in every complete run, so comparisons
with addr15000 use 387-841.

**Order.** ABBA cancels a linear drift in the mean of the two reps. It does not
cancel the r1/r2 effect found here (below).

**Adversarial review** (`review.json`). Five skeptics attacked nine draft claims
(C1-C9), one or two each. The eight they challenged went to adjudicators, one
per claim, who resolved each against the raw data. One claim was confirmed;
eight were corrected, none refuted. Two code reviewers found no defect in the
benchmarked path but two latent crash risks, fixed above. A critic listed
confounds and missing measurements. **Every figure here is the post-review
figure.**

## Results

### Warm: profile order at 15000 MiB is 31% faster than pageable

Tokens 387-1022, mean of r1 and r2, ms per token (`analysis.md`):

| arm | ms/token | vs off | r1 / r2 | compute | DMA | idle | slow-copy idle | fast-copy idle | pinned share of upload bytes |
|---|---:|---:|---|---:|---:|---:|---:|---:|---:|
| off | 52.95 | - | 53.65 / 52.25 | 13.02 | 26.86 | 12.95 | 3.00 | 6.07 | 0% |
| addr7842 | 43.97 | -17.0% | 44.83 / 43.12 | 12.96 | 22.69 | 8.20 | 1.50 | 3.01 | 49.3% |
| prof7842 | 40.42 | -23.7% | 41.08 / 39.76 | 12.96 | 20.08 | 7.26 | 2.10 | 1.40 | 77.7% |
| addr15000 | 39.17 | -26.0% | 39.58* / 38.77 | 12.92 | 20.01 | 6.12 | 0.88 | 1.44 | 79.8% |
| prof15000 | **36.43** | **-31.2%** | 36.66 / 36.20 | 12.89 | 18.23 | 5.19 | 0.91 | 0.53 | 97.7% |
| none | 37.93 | -28.4% | 38.13 / 37.72 | 12.89 | 19.71 | 5.21 | 0.01 | 1.50 | 81.5% |

\* addr15000_r1 covers 387-841 only (455 tokens).

Matched window 387-841: off 53.52, addr7842 44.40, prof7842 40.70, addr15000
**39.35**, prof15000 **36.65**, none 38.21.

Whole run (3-1022): off 56.20, prof15000 36.56 (-35.0%).

### Profile order beats address order at both caps

Paired by round (negative: the first arm is faster):

| pair | window | mean | r1 | r2 |
|---|---|---:|---:|---:|
| prof7842 - addr7842 | 387-1022 | **-3.55 ms (-8.1%)** | -3.75 | -3.36 |
| prof15000 - addr15000 | 387-841 | **-2.69 ms (-6.8%)** | -2.68 | -2.71 |
| prof15000 - addr15000 | 387-1022, r2 only | -2.57 ms (-6.6%) | | |
| prof7842 - addr15000 | 387-841 | +1.35 ms (+3.4%) | +1.86 | +0.84 |
| none - addr15000 | 387-841 | -1.14 ms (-2.9%) | -1.16 | -1.12 |
| none - prof15000 | 387-841 | +1.56 ms | | |

- Both profile gains have the same sign in both rounds and in every 128-token
  window of each round. prof15000 is faster on 84-87% of paired tokens.
- prof7842 pinned 101 MiB more than addr7842. The offline model puts that at
  about 0.9 points of pageable share, about 0.1 ms of the 3.55 ms gap.
- **Profile order at the default cap does not match address order at 1.9x the
  pinned memory.** prof7842 is 1.35 ms behind addr15000 on matched tokens. The
  per-token median gap is only 0.1-0.4 ms, and prof7842 is faster on 42-49% of
  paired tokens, so the mean gap comes from a tail of slow pageable copies:
  slow-copy idle is 2.18 against 0.91 ms on the same tokens.
- addr15000 is a handicapped reference: it ran near memory starvation (below),
  and one rep was killed. Against `none` instead, prof7842 is 6.6% slower.

### Where the gain comes from

Of the 16.52 ms between off and prof15000 (warm), **DMA plus fast-copy idle is
14.17 ms (86%)** and slow-copy (page-fault) idle 2.08 ms (13%; 19% in r1, 6% in
r2). Across the other arms the slow-copy share is 7-20%. Compute is 12.89-13.02
ms everywhere.

Copy rates (CUPTI, GPU side, expert copies):

| source | GB/s |
|---|---:|
| pinned: addr7842, addr15000, prof15000, none | 12.75-12.85 |
| pinned: prof7842 | 11.9-12.0 |
| pageable: off | 8.56-8.70 |
| pageable: addr arms, none | 8.5-8.9 |
| pageable: prof arms | 10.5-11.3 |

The pageable rate depends on the arm. In the profile arms the pageable copies
are fewer and rarer, so the host is less often staging one copy while the next
one runs. "Fast-copy idle" may include soft (transition) faults as well as
staging: off still has 788-831 transition faults per token warm, against
172-214 for `none`. The label stays "DMA rate plus host-side idle inside fast
pageable copies" until a staging microbenchmark (Q14) splits the two.

Hit counters are identical in all 11 completed runs: hits 203847, misses
123521 (62.27%), 227643.19 MiB uploaded, large batches 5707.74 MiB. **Pinning
changes neither routing nor cache behaviour.**

### The offline coverage model predicts the pageable share

| arm | predicted (offline, tokens 16-255) | measured, tokens 16-255 | measured, 387-1022 |
|---|---:|---:|---:|
| addr7842 | 53.8% | 53.8 / 53.8 | 50.7% |
| prof7842 | 20.7% | 20.6 / 20.6 | 22.3% |
| addr15000 | 21.3% | 21.4 / 21.4 | 20.2% |
| prof15000 | 2.1% | 2.1 / 2.1 | 2.3% |

Within the window the traces cover, the replay matches CUPTI to 0.1 points. That
checks the simulator and the address mapping; it is a replay of the same
deterministic routing, not a prediction for unseen text. Beyond the traces'
255 tokens the share drifts by up to 4.4 points: prof7842 is 25.1% over tokens
256-386.

**Generality of the profile.** It is held out at the prompt level only. Prompts
b and c share the technical domain of prompt a (caching, memory hierarchy), and
a, b and d open with the same thinking scaffold. Prompt a is the best-covered of
the four offline (2.1% pageable at 15000 MiB against 4.6-5.7%; 20.7% at the
default cap against 26.8-29.3%). So the measured gain is likely optimistic for
other prompts, especially at the default cap, where the profile's cutoff falls
at 16 selections. At 15000 MiB it falls at 1: every expert the 765 profile
tokens selected at least twice is pinned, but only 207 of the 606 selected once
(8126 of the 8525 experts the profile saw).

**An online profile would do almost as well** (offline, no code): counting
selections over a run's own first 64 or 128 tokens and pinning then leaves
5.5-7.6% or 2.8-4.2% pageable at 15000 MiB over tokens 128-255 (four traces),
and 17.9-25.5% or 13.6-22.4% at the default cap. Scored on 128 tokens only.

### Cost of profile pinning

- **Registration**: 0.26-0.27 s for 4881 ranges, 0.64 s for 7299 ranges,
  including about 16 ms of profile parsing, against 3-4 ms for address order's
  50-96 ranges. Raw ready-time differences against the same-cap address arm
  (+0.18 to +0.95 s) are mostly model-load variation.
- **More copies.** The split adds sub-page slivers where pinned and pageable
  ranges meet. Warm, there are 520.1 `cudaMemcpyAsync` calls per token for
  prof7842 and 462.0 for prof15000, against 450.3 in the other arms. The extra
  calls are all small; total bytes are unchanged. Pinned host-to-device copies
  under 4 KiB: 79629 in prof7842_r2 against 7167 in addr7842_r2, about +0.4 s
  of API time and +0.17 s of GPU time over the run. That is about 1% of a
  prof7842 token, already inside its measured time.

### The pinned-memory budget, and what `--load-mode none` really pins

`cudaMallocHost` gave 14848 MiB in 512 MiB chunks and refused the next one
(`pin_budget.txt`). The none run below pinned about 15240 MiB, and an earlier
sweep (Finding 4) registered 15266 MiB, so the budget moves a little with the
state.
**This host's pinned budget is about 15 GiB, about half of RAM** (level 1).

`--load-mode none` logs one 19275.31 MiB `CUDA_Host` buffer. But the CUDA host
buffer type caps a buffer at 4 GiB
(`ggml_backend_cuda_host_buffer_type_get_max_size`), so the loader splits it
into five chunks: about 4037, 4000, 4032, 4032 and 3174 MiB. When
`cudaMallocHost` fails for a chunk, it silently falls back to a pageable CPU
buffer:
- the failure is logged only at debug level, below `-lv 4`;
- the multi-buffer keeps the first chunk's `CUDA_Host` name.

Here the fourth chunk fell back: layers 25-32, plus one tensor each of layers
24 and 33. CUPTI agrees: pageable traffic appears only in those layers. So the
`none` arm is **about 80% pinned** (18.5% of warm upload bytes pageable). Its
pageable part sits in private memory, not the file mapping, so it does not
fault (0.01 ms slow-copy idle). It loads in 14.8-15.2 s instead of 6.3-7.5 s.

### Memory headroom: profile order leaves more RAM free

Measured from token 387 to the last token (typeperf rows aligned to the run):

| arm | available RAM, median (r1 / r2) | pinned | left pageable |
|---|---:|---:|---:|
| addr15000 | **243 / 814 MiB** | 14946 MiB | 3814 MiB |
| prof15000 | **1764 / 2336 MiB** | 14924 MiB | 3837 MiB |

- The gap is about 1.0 GiB at decode token 3. It grows to 1.61-1.70 GiB
  (1653-1736 MiB) by token 387 and falls back to about 1.36-1.42 GiB
  (1396-1455 MiB) by the end.
- In address order the pageable 3.72 GiB are whole layers 32-39, used at the
  normal rate, so their popular experts probably join the working set early
  (residency was not measured).
- In profile order the pageable experts are the rarely selected ones, so fewer
  of them have been touched at any point.
- This is cumulative, not a lower ongoing fault rate. In the warm window, profile
  order adds new pages faster (0.77-0.87 against 0.19-0.36 MiB per token), and
  the hard-fault rates of the two arms are the same (0.64/0.46 against
  0.62/0.42 slow copies per token).
- Whether the advantage persists past 1024 tokens is not shown.
- addr15000_r1 hit the floor and was killed. addr15000_r2's warm minimum was
  724 MiB.

**At about 15 GiB pinned of 31, the desktop is close to the edge.** Address
order took it over once.

### R10: a fixed launch state, but not a fixed run

Eviction made the page cache reproducibly cold at launch: 0-7 of 256 probed
expert pages were cached before all 12 runs. **Reps still did not agree within
3%.**

| arm | warm r1 - r2 | warm spread | tokens 3-130 spread | prefill slow copies r1 / r2 |
|---|---:|---:|---:|---|
| off | +1.40 ms | 2.6% | 27.5% | 604 / 44 |
| addr7842 | +1.71 | 3.9% | 18.1% | 465 / 37 |
| prof7842 | +1.32 | 3.3% | 11.2% | 322 / 97 |
| addr15000 | +0.47 (387-841) | 1.2% | 15.2% | 335 / 78 |
| prof15000 | +0.46 | 1.3% | 2.4% | 144 / 148 |
| none | +0.41 | 1.1% | 3.5% | 1 / 1 |

- **r1 was slower than r2 in all six arms.** In the pageable arms the excess is
  slow-copy (page-fault) idle that decays with token index: off warm 4.34
  against 1.65 ms. The r1 - r2 difference in off falls from 18.8 ms in tokens
  3-130 to 0.3-0.6 ms in the last windows.
- **Available RAM rose through the session.** Before eviction it was 20202 and
  20140 MiB (19.73 and 19.67 GiB) for the first two runs and 21642 and 21644 MiB
  (21.13 and 21.14 GiB) for the last two. It was 17500 MiB (17.09 GiB) at the
  session's first eviction, before the smoke and B3 runs. Each eviction trims
  other processes, so the likely cause is other processes being trimmed and not
  growing back. That is plausible but not measured.
- **Position and headroom cannot be separated.** The time between an arm's two
  reps correlates with its r1 - r2 at r = 0.88 (0.91 with addr15000's unmatched
  +0.81 ms), the RAM change with r1 - r2 at r = 0.70 (0.79), and the two with
  each other at r = 0.86. The stable arms (prof15000, none) are also the ABBA
  inner pairs, run 2-7 minutes apart. So their stability cannot be credited to
  having little file-backed pageable traffic.

**Tokens 3-130 are early, not cold.** The load's whole-file prefetch had read
15.7-19.2 GiB before the first large host-to-device copy (non-expert weights),
about 19.1-20.7 GiB before the first expert copy, and 19.5-20.8 GiB by the end
of prefill. Disk reads during tokens 3-130 were only 0.04-1.47 GiB. What that
window adds is soft (transition) faults, re-faults and, in some runs, hard
faults (off_r1 read 1.47 GiB). Transition faults:
- off: about 8600 transition faults per token;
- addr7842: 5100-5200;
- prof7842: 4300-4700;
- addr15000: 2300;
- prof15000: 700-800;
- none: 135-142.

So the 3-130 percentages in `analysis.md` (for example prof15000 -46.5% against
off) are indicative only. EXP-0004's cold window had 91.7 ms per token of
slow-copy idle; off here has 15.22 ms (r1 25.4, r2 5.0).

### Prefill depends on how much of the file the load leaves unread

**Level 4 (hypothesis; the observations behind it are level 1).**
- Available RAM before the runs was 19.7-21.1 GiB against the 20.82 GiB file,
  below the file in 7 of 12 runs.
- After eviction, the mmap arms prefilled in 1.55-3.02 s with 37-604 slow
  copies (of 6630-7728).
- EXP-0004's pageable runs that followed other pageable runs took 13.4-13.8 s
  with 6423-6487 of 6630 slow, at 16.5-17.3 GiB available.

Here the load did not read the whole file:
- The load burst read 19.05-19.78 GiB in r1 and 20.24-20.38 GiB in r2, about
  0.5-0.8 GiB below available RAM.
- The experts that were slow at prefill are the unread tail by GGUF offset:
  layers 36-39 (off_r1, addr7842_r1), 37-39 (addr15000_r1), 39 (every r2
  off/addr run).

So prefill page faults probably scale with available RAM, through how much of
the file's tail the load leaves unread. RAM shortfall alone does not explain
EXP-0004, though:
- The same tail pattern would leave about the last 9-10 layers missing there,
  yet all 40 were.
- At the same RAM, prior state set the regime. Pageable runs right after a
  pinned run prefilled in 3.7-7.3 s; after pageable runs, 13.4-13.6 s.

The r1/r2 contrast is confounded with session order. The cross-session contrast
also differs in procedure, code and other processes. A direct test holds a fixed
balloon allocation per run (ROADMAP R16).

### The copy-edge rule

`cross_copy.py` registers one 4 KiB page (Portable, ReadOnly) and copies around
it with cudart 12.6. The test covers one VirtualAlloc'd page, not a file
mapping, on one driver.

| copy | `cudaMemcpy`, `cudaMemcpyAsync` |
|---|---|
| inside the registered page | 0, 0 |
| starts in it, ends one byte past it | **1, 1** (cudaErrorInvalidValue) |
| starts in it, runs into the next page | **1, 1** |
| starts 512 B in, runs into the next page | **1, 1** |
| starts before it, ends inside it | 0, 0 |
| starts before it, runs past it | 0, 0 |

So a host-to-device copy must not start in registered memory and run past its
end (level 1).
- **Address order never triggers it.** Whole tensors are pinned, and a copy
  never spans two tensors.
- **Expert-level pinning triggers it constantly.** Every expert tensor starts
  off a page boundary (data start 10990048, alignment 32). So a pinned expert's
  page-rounded range covers the first partial page of its neighbour, and a fill
  of that neighbour starts inside the range.
- The first expert-pinned smoke run died in
  `ggml_backend_cuda_set_tensor_async` with `invalid argument` during prefill.
  Its log was overwritten by the rerun; only this record and `cross_copy.py`
  keep it.

### Incidental

- The none arm's pageable experts sit in private memory, yet it still shows
  0.10-0.65 GiB of disk reads and up to about 1 MiB per token of pages input in
  the warm window. That is other processes paging back in after the eviction.
  **The system-wide disk and paging counters are not llama-only.** Whole-run
  disk reads of 21.3-23.7 GiB include 0.9-4.7 GiB read after the load burst: in
  the mmap arms partly llama's own page faults (on the file's unread tail and
  during decode), and partly such page-ins.
- typeperf rows stall up to 5.5 s during model loads. Disk totals must integrate
  the rate over each real interval. Summing rows as 1 s each undercounts the
  mmap runs 1.8-4.3x (`calib_disk_counter.txt`).

## Correctness

**The pinning changes are byte-exact.** The B3 gate itself was found to be
partly a CPU-vs-GPU comparison.

1. **B3 as it was (64 tokens): 9 of 9 OK** (`b3_correctness.txt`), including
   `cache2048-pinprof` at 15000 MiB, on the benchmarked build.
2. **The 1024-token outputs** in the Nsight captures of all 11 completed timed
   runs are byte-identical, both profile arms included. The stopped
   addr15000_r1's output is a prefix of them.
3. **B3 at 256 tokens on the post-review build: every configuration differed
   from cache-off** (`b3_correctness_ngen256.txt`). But the outputs fall into
   three groups by cache size, not by pinning:
   - cache-off;
   - all five 1024 and 2048 MiB configurations, pinned and profile-pinned
     included;
   - all four 528 and 256 MiB configurations.

   The cache-off text first differs at byte 535; the 64-token text ends at byte
   522 (a 524-byte file with two trailing newlines). So the old gate stopped a
   few tokens short of the divergence. 528 MiB diverges from 2048 at byte 734,
   about token 110.
4. **Cause: where the experts are computed.** With the cache off, a decode token
   runs the experts on the CPU, because they are host weights and the batch is
   under the offload threshold of 32. At 528 and 256 MiB one cache group gets no
   slots (`budget is too small for 1 layers, they are not cached`), and that
   layer also runs on the CPU. CPU and CUDA kernels quantize activations and
   accumulate differently. Test: with `GGML_OP_OFFLOAD_MIN_BATCH=1`, which
   offloads every expert matmul to the GPU, cache-off and 528 MiB both produce
   exactly the 2048 MiB text (level 1).
5. **B3 with every configuration on the GPU, 256 tokens: 10 of 10
   byte-identical** (`b3_correctness_gpu256.txt`):
   - cache-off;
   - the six eviction variants at 528 and 2048 MiB;
   - 256 MiB, and pinning at 1024 MiB;
   - profile pinning at the default cap (7299 ranges, the most split edges).

   The reference is identical to what the default 2048 MiB cache generates.
   `check-correctness.sh` now runs this way by default.
6. **Smoke runs on the post-review build**
   (`smoke_v2_prof7842_lines.txt`, `smoke_v2_badprofile_lines.txt`):
   - The profile at the default cap registers the same 7943.22 MiB in 7299
     ranges, with the same hit counters.
   - A file with no selections logs a warning and pins 7842.20 MiB of whole
     tensors in 50 ranges.

**Consequence beyond this experiment.** KNOWLEDGE_BASE.md's correctness
invariant said generation "must be bit-identical" with the cache off. That holds
only with the experts computed on the same device. Comparisons at the same
cache size are unaffected, because every policy at one size computes the same
layers on the same device. But hardware rows at 256-586 MiB decode a different
text than 2048 MiB after about 100 tokens. How much that moves their hit rates
is not measured (OPEN_QUESTIONS.md Q15).

## Conclusions

**Decision: Adopt** `LLAMA_MOE_PIN_PROFILE` and the edge split. The default
pinning stays as it was: opt-in, address order, RAM/4.

1. **R11 holds on this host.** Pinning near the budget takes the warm 2048 MiB
   token from 52.95 to 36.43 ms (-31%). That is below EXP-0004's projection for
   the cap (38-39 ms) and within 2 ms of its bound for pinning every expert
   (34.6), though those were projected from another session's 56.2 ms.
2. **Order is worth about three quarters of doubling the pinned size at the
   default cap** (-3.71 ms at the same MiB against -5.05 ms for address order at
   1.9x the MiB, tokens 387-841). Over tokens 387-1022 profile order gets -8.1%
   at the same MiB. At 15000 MiB it is -6.8%, and it leaves about 1.4 GiB more
   RAM available.
3. **Most of pinning's warm gain is DMA time plus host-side idle inside fast
   pageable copies, not slow-copy (hard-fault) idle** (86% against 13%). That
   confirms EXP-0004's split with a far larger pinned share.
4. **`--load-mode none` is not "full pinning".** It is about 80% pinned through a
   silent per-chunk fallback, and takes twice as long to load. It beats address
   order but not profile order, and it pins whatever chunks fit, with no control
   over which.
5. **Fixing the launch state did not fix the run.** The page cache refills from
   the load's prefetch, and how much depends on available RAM, which drifted.
   R10 needs headroom held constant, not only the cache evicted.
6. **The correctness gate needed fixing.** It now compares like with like: every
   configuration computes the experts on the GPU, and it runs 256 tokens.

### Limitations

- One host, one model, one cache size (2048 MiB, 62.27% hits), batch 1, greedy,
  one run prompt, and a profile from the same domain.
- Two reps per arm. The warm pair differences hold in both rounds and in every
  128-token window. The rep-to-rep drift (0.4-1.7 ms) is as large as the
  prof7842 - addr15000 gap.
- Every number is traced. Nsight adds about 2.4 us per API call, about
  0.17 ms per prof7842 token from the extra calls. The comparison is
  conservative, but the untraced magnitude was not measured, and the B2
  reconciliation and persistent-process parts of R10 were not done.
- The results are for tokens 387-1022 of one 1024-token generation in a fresh
  process. Pageable arms still fault in the warm window (off 0.95-2.54 slow
  copies per token).
- The eviction trims every other process, so system-wide counters include their
  page-ins. RAM headroom drifted 1.5 GiB across the session.
- How much profile order wins depends on the cap relative to the expert bytes.
  With RAM to pin everything (or no WDDM budget), order would not matter.
- The review fixes (process-wide table, scheduler fallback) are verified by B3
  and smoke runs, not re-timed. The multi-context path is untested.
