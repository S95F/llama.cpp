# EXP-0001 - Re-validate the simulator on base `d854d98b`

**Status: complete. Decision: Adopt.** Iteration 1, authorized 2026-10-26.

Roadmap item **R1**. Infrastructure, not an optimization: it produces no speedup
and is expected to produce no code change.

## Hypothesis

Two parts, both falsifiable:

- **H1** - `moe-bench/moe_sim.py` still reproduces llama.cpp's cache counters to
  the digit on base `d854d98b`, as it did on `78a8ae1`.
  **Falsified by** a simulated hit rate or uploaded-byte count that misses the
  measured one by more than the 0.7 to 0.8 points already attributed to the two
  implementations drawing different RNG streams. At 2048 MiB the branch is inert
  (`n_sample = 0`) so the comparison is against the deterministic `slru-ramp`
  policy, where the agreement should be **exact**, not within a margin.
- **H2** - the policy rankings of KNOWLEDGE_BASE.md Findings 2, 3 and 6 are
  unchanged by upstream's router perturbation.
  **Falsified by** any reordering of the policy table, or by a change in the
  crossover position.

## Motivation

Upstream's own commits between `78a8ae1` and `d854d98b` changed the router's
top-8 at some positions. This is measured (level 1): with `--moe-cache-mib 0`,
where the cache is never constructed, the two bases generate different text from
the same greedy decode. Attribution to `c49edf096` and `a55c16e4e` is level 4.

Consequence: all four traces behind every simulated table in the knowledge base
were collected on the old base, so **no simulated number is currently quotable
for the base the branch sits on**. That blocks ROADMAP R2 and R3, which are
policy experiments meant to be screened by the simulator rather than validated
one candidate at a time on hardware.

Related: OPEN_QUESTIONS.md Q1 (this experiment), Q2 and Q7 (both answerable
offline from the traces this experiment collects, at no extra GPU cost).

## Previous experiments this depends on

EXP-0000, which established the simulator's bit-exactness on `78a8ae1`
(2048 MiB: simulator 60.82% / 58867.3 MiB uploaded / 2044.1 MiB VRAM against
llama.cpp 60.82% / 58867.26 / 2044.11) and measured the `d854d98b` hardware
counters this experiment compares against.

agents were present but idle, which the protocol does not count as a running
game.

## Benchmark commands

Collection, `research/results/experiments/EXP-0001/collect.sh`, one process at a
time:

```sh
export PATH="/c/Users/steve/cuda126/bin:$PATH"   # build/ links CUDA 12.6, not the system 13.2
LLAMA_MOE_CACHE_TRACE="$OUT/trace_$p.csv" ./build/bin/llama-completion \
    -m "$MODEL" -ngl 99 -ncmoe 40 --moe-cache-mib 2048 \
    -c 2048 -n 256 -f "moe-bench/$p.txt" --temp 0 --seed 1 \
    -t 8 --no-warmup -no-cnv -v
```

for `p` in `prompt`, `prompt_b`, `prompt_c`, `prompt_d` - technical prose, C++
code, a history summary, and a translation task. Each run is 40 layers x 255
tokens = 10202 slot-map copies.

Validation, against the counters from the same runs:

```sh
python moe-bench/moe_sim.py "$OUT/trace_prompt.csv" \
    --layout moe-bench/layout-qwen35moe-35b-a3b-ud-q4kxl.json \
    --sizes 2048 --policies slru-ramp --json "$OUT/sim_validate.json"
```

Policy sweep:

```sh
python moe-bench/moe_sim.py "$OUT/trace_$p.csv" \
    --layout moe-bench/layout-qwen35moe-35b-a3b-ud-q4kxl.json \
    --sizes 256,384,528,586,645,1024,2048 \
    --policies slru-ramp,ramp-s16-age8,lfu,s3fifo,ramp-rand,belady \
    --json "$OUT/sim_sweep_$p.json"
```

Note on why a trace taken at one cache size may be replayed at any other: the
trace records the expert ids the router selected, routing depends only on the
model and the text, and the cache is known not to change generated output
(KNOWLEDGE_BASE.md correctness invariant). So the selection sequence is
independent of cache size and policy.

## Results

Collection took 4 minutes for all four traces (06:12:29Z to 06:16:33Z). Each
trace is 10202 lines = 10201 generation-sized slot-map copies over 40 layers,
matching EXP-0000's count exactly.

### H1 - simulator bit-exactness: CONFIRMED, exactly, on all four traces

At 2048 MiB the branch is inert, so the active policy is `slru-ramp` and the
comparison should be exact rather than within a margin. It is - the simulator
reproduces the individual hit and fill **counts**, not just the ratios:

| trace | simulator hits / fills | llama.cpp hits / misses | hit rate | uploaded MiB |
|---|---|---|---:|---:|
| prompt | 50092 / 31516 | 50092 / 31516 | 61.38% both | 58033.625 vs 58033.62 |
| prompt_b | 49846 / 31762 | 49846 / 31762 | 61.08% both | 58497.4 vs 58497.38 |
| prompt_c | 53248 / 28360 | 53248 / 28360 | 65.25% both | 52297.4 vs 52297.39 |
| prompt_d | 48715 / 32893 | 48715 / 32893 | 59.69% both | 60505.3 vs 60505.34 |

VRAM also matches: simulator 2044.109375 MiB against llama.cpp's 2044.11.

This is **stronger than EXP-0000's validation**, which checked one trace and
reported agreement to 2 decimal places. Here the integer counts agree, so the
simulator is replaying the same decisions, not merely landing on the same
aggregate.

The `prompt` row at 2048 MiB (61.38%, 58033.62 MiB) is also **byte-identical to
the figure recorded in a different session** (BENCHMARKS.md B1 reference for
`d854d98b`), which independently confirms that the deterministic metrics
reproduce across sessions on this machine.

flips where the mean is small:

### Refinements to two rejected policies

Both remain rejected; the characterisations in FAILED_APPROACHES.md were
imprecise and are now corrected.

- **Full LFU** was recorded as "wins below the crossover but loses up to 5 points
  above it". More precisely: it wins only at **256 MiB** (+0.63 mean, and not
  sign-consistent - three of four traces), is a wash at 384, and **loses from 528
  MiB upward**, including below the crossover (-2.73 at 528, -2.97 at 586). Above
  the crossover it loses 2.8 to 5.8 points against the policy that actually ships
  there (`slru-ramp`): 56.01 vs 61.85 at 2048.
- **S3-FIFO** was recorded as "erratic at the small sizes". It is worse than that
  at the smallest size: **0.00% at 256 MiB**, a complete failure matching plain
  LRU. It does beat `ramp-s16-age8` at 2048 by 2.20 points, but not the policy the
  branch actually uses there - `slru-ramp` beats it 61.85 to 60.97. Its large-cache
  advantage from EXP-0000 was measured at 6144 MiB, which was not re-tested.

### Routing skew: mechanism holds, the quantitative range widened

Finding 2 re-measured on the new traces (`trace_stats.txt`):

| hottest k of 256 | reference range | now | prompt_d alone |
|---:|---:|---:|---:|
| 8 | 31 - 33% | **25.9 - 33.2%** | 25.9% |
| 16 | 46 - 47% | **39.1 - 46.8%** | 39.1% |
| 32 | 64 - 66% | **57.0 - 65.7%** | 57.0% |
| 64 | 83 - 85% | **79.1 - 85.1%** | 79.1% |

**The widening is entirely `prompt_d`**, the multilingual translation task; the
other three traces sit inside the reference ranges. Even `prompt_d` is strongly
skewed - 79.1% of selections from the hottest 64 of 256 experts, against 25% for
uniform routing - so the mechanism behind Finding 3 is intact, and `prompt_d` is
also where the sampled victim beats LFU by the widest margin (+4.83 to +6.08).

The cause is expected rather than surprising: greedy decode diverges between the
two bases, so after the first divergent token the traces cover **different
generated text**, not the same text with slightly different routing. A
multilingual continuation is the one most likely to drift in character. This is
a quantitative refinement of Finding 2, not a reversal, but the old narrow ranges
should not be requoted.

Token-to-token overlap, which is what killed the prefetch idea, also shifted up
slightly: t-1 31.4 to 38.7% (reference 31 to 37%), t-8 19.6 to 25.3%
(reference 19 to 23%). Still far below the 79 to 85% that the hottest 64 deliver,
so the rejection stands.

## Correctness and regression

No source change, so the correctness gate (BENCHMARKS.md B3) is not re-run
for this experiment. It will be re-run before any policy change from R2 or R3.

The strongest correctness evidence here is incidental: the simulator, an
independent Python reimplementation, reproduces llama.cpp's hit and fill counts
exactly on four traces. A bug in either would have to be mirrored in both.

## Conclusions

**Decision: Adopt.** Both hypotheses confirmed. The deliverable is
infrastructure, and it is now in place:

- The simulator is **validated on `d854d98b`** and may be used to screen policies
  without GPU time. This unblocks ROADMAP R2 and R3.
- The four traces, the simulator output and the aggregation script are
  **committed**, which no prior measurement in this project was.
- Every simulated figure in KNOWLEDGE_BASE.md is now quotable for the current
  base, with the deltas recorded above.

**No performance claim is made and no code changed.**

### Limitations

1. **No throughput measured.** 12.34 GiB free host RAM against an 18.32 GiB
   working set would have made timing dominated by page-cache misses. Deliberate.
2. **One cache size validated bit-exactly.** 2048 MiB is the only size where the
   branch is inert and the policy therefore fully deterministic. Below the
   crossover the two implementations draw different RNG streams, so exact
   agreement is not expected there and was not tested; EXP-0000 measured that
   gap on hardware at 0.7 to 0.8 points.
3. **`slru-ramp` only.** The validation covers the policy that runs at 2048 MiB.
   The sampled policy's own C++ path is validated only indirectly, through
   EXP-0000's hardware measurements below the crossover.
4. **Four prompts, one model.** `prompt_d` alone moved Finding 2's range by 5
   points, which is a warning about how few traces four is.
5. **Belady at 645 MiB** has no reference value; section 8 did not tabulate it.
